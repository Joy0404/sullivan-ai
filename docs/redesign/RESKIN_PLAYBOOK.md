## 0. Codex에게: 이 파일 읽는 법

- **한 번에 전부 읽지 말 것.** 사용자가 지정한 작업(T0~T6)에 해당하는 절만 읽는다. 항상 읽을 것은 1·2·3·4·9절이다.
- 이 파일과 코드가 다르면 **코드를 기준으로 사실을 확인**하고, 다른 점을 보고한다. 추측으로 채우지 않는다.
- 작업을 시작하기 전에 **계획만 먼저** 보여주고, 사용자가 "진행해"라고 하면 구현한다.
- 끝나면 10절 "보고 형식"대로 보고한다.

### 파일 위치 (저장소 기준)
```
docs/redesign/RESKIN_PLAYBOOK.md   ← 이 파일
docs/redesign/PROMPTS.md           ← 작업별 시작 프롬프트
docs/redesign/current/*.jpg        ← 현재 보호자 화면 + 문제 위치 빨간 번호 (우리 앱 화면)
docs/redesign/refs/*.jpg           ← 레퍼런스 캡처 (다른 회사·기관 화면, 커밋 금지)
```
`.gitignore`에 `docs/redesign/refs/`가 들어 있어야 한다. 없으면 T0에서 추가한다.

## 1. 무엇을 만드나

**한 문장:** 보호자가 소개 페이지를 보고 "써 보고 싶다"고 느끼고, 가입 후 학생 세팅을 헤매지 않고 끝내도록 보호자 경험을 다시 만든다.

| 만드는 것 | 경로 | 상태 |
|---|---|---|
| 보호자 소개 랜딩 | `/intro/` → `apps/web/intro/index.html` | 새로 만듦 |
| 보호자 사용 가이드 | `/guide/` → `apps/web/guide/index.html` | 새로 만듦 |
| 보호자 화면 리스킨 | 기존 `apps/web/index.html`의 보호자 영역 | 고침 |
| 학생 화면 | 기존 | **동결**(버그 2건만 수정) |

### 왜 (배경)
- 이 서비스는 **보호자가 학생 계정을 만들고 강의를 배정해야** 학생이 쓸 수 있다. 보호자가 막히면 학생은 시작도 못 한다.
- 지금은 소개 페이지가 없고 첫 화면이 바로 로그인이다.
- 보호자 화면은 기능은 다 있지만 무엇부터 할지, 어디까지 했는지가 안 보이고, 기술 용어가 많다(4절).
- 학생 화면은 큰 버튼 4개로 단순해서 오히려 좋다. 그래서 건드리지 않는다.

### 서버 구조에서 확인한 사실
- `apps/api/app/main.py`가 `apps/web`을 `/`에 `StaticFiles(html=True)`로 서빙한다. → `apps/web/intro/index.html`만 만들면 `/intro/`로 열린다. **서버 코드 수정 불필요.**
- 계정은 로컬 SQLite(`data/private/accounts.sqlite`)다. 공개 회원가입은 범위 밖이다. 랜딩의 "보호자로 시작하기"는 `/`(로그인 화면)로 보낸다.
- 샘플 데이터 `sample-catalog.json`은 로그인 없이 받아진다. 다만 지금 화면은 로그인 후에만 샘플을 연다.
- `progress` 테이블에 학생별 위치·밑줄·북마크·메모가 저장된다. **저장 시각은 없다.**

## 5. 스킬 사용 계획

이 프로젝트에는 4차 멘토링 때 아래 스킬을 설치했다. **설치된 정확한 이름은 먼저 확인**한다("설치된 스킬 목록 보여줘"). 이름이 다르면 가장 비슷한 것을 쓰고 보고한다.

| 스킬 | 이번 작업에서의 역할 | 언제 |
|---|---|---|
| `hallmark` | 디자인 방향 정하기 + 마지막 점검(finish review) + 작업 기록(CSS 맨 위 주석) | 각 작업 시작(방향)과 끝(점검) |
| `frontend-design` | 랜딩의 구성·타이포·여백 등 "보이는 인상" 잡기 | T1 랜딩 |
| `web-design-guidelines` | 만든 화면 코드를 UI 가이드라인으로 검토 | 구현 직후 |
| `accessibility` | 접근성 감사(WCAG, 키보드, 스크린리더 이름, 대비) | 구현 직후, 보고 전 |
| `security-best-practices` | 새 API의 권한 검사 확인 | T5만 |

**규칙: 스킬을 쓰기 전에 해당 스킬의 `SKILL.md`를 먼저 읽고 그 절차를 따른다.** 이 플레이북이 스킬 사용법을 대신하지 않는다. 플레이북은 "무엇을, 어떤 범위로"만 정한다.

### 5-1. 모든 작업 공통 순서 (파이프라인)
```
1) 계획      : 이 파일의 해당 절 + 필요한 이미지만 읽고 계획 제시 → 사용자 승인
2) 방향      : hallmark(필요하면 frontend-design)로 디자인 방향을 3~5줄로 정리
3) 구현      : 범위 안 파일만 수정. 작은 단위로.
4) 검토      : web-design-guidelines → 지적 사항 수정
5) 접근성    : accessibility → 위반 수정
6) 마무리점검 : hallmark finish review → 남은 문제 기록
7) 검증      : bash scripts/verify_all.sh, 학생 파일 diff 확인, 1280/390 캡처
8) 보고      : 10절 형식
```

### 5-2. hallmark에 줄 설정 (지난번과 다르게)
지난 11/3 작업은 CSS 주석에 `redesign: polish`, `genre: modern-minimal (inferred)`로 남았다. 즉 **기존 모양을 조금 다듬기만 했고, 분위기는 AI가 추측**했다. 이번에는 아래를 **직접 알려 준다**(정확한 입력 방식은 hallmark SKILL.md를 따른다).

- 범위(scope): 보호자 화면 + `/intro/` + `/guide/`. **학생 화면 제외.**
- 재설계 정도: 보호자 화면은 전면 재설계(full). 단, 색·글꼴 토큰(`tokens.css`)은 유지.
- 분위기(genre): "차분하고 믿음직한 교육 서비스". 키워드: 안심, 명료, 따뜻함, 공공 서비스 수준의 접근성.
- 피할 것: 화려한 그라데이션, 장식용 애니메이션, 작은 회색 글자, 아이콘만 있는 버튼.
- 예외 유지: 학생용 큰 버튼(64px·80px) 관련 기존 waive 기록은 지우지 않는다.
- 레퍼런스: 3절 표의 해당 이미지.

랜딩에만 강조색 1개를 추가할 수 있다(배경 대비 4.5:1 이상 확인).

### 접근성 (보호자도 저시력일 수 있다)
- 본문 18px 이상, 버튼 높이 48px 이상, 200% 확대·폭 320px에서 가로 스크롤 없음
- 상태는 **색 + 글자** (완료 / 할 차례 / 아직 / 기본값)
- `lang="ko"`, 모든 이미지 `alt`, 제목 순서 h1→h2→h3, "본문 바로가기"
- Tab만으로 전체 흐름 가능, 포커스 항상 보임
- 애니메이션은 `prefers-reduced-motion`이면 끔. 스크롤에 따라 나타나는 애니메이션 금지
- 펼침은 `<button aria-expanded>` 또는 `<details>`
